# プロダクトビジョン＆ユースケース戦略：InstantMesh

> **2026-07-27 方向転換**: 前面に出す姿を「汎用のアカウントレス一時メッシュVPN」から「**ローカルAI／MCP を、公開せずに一時的に人へ貸すためのアクセス層**」へ寄せた。汎用メッシュ機能は削らず土台として残す。判断の根拠と経緯は `docs/要件定義書.md` 付録C を参照。

## 1. 解決するコアな課題（Why InstantMesh?）

ローカルAI（Dify＋ローカルLLM、MCP サーバー等）の現場には、性質の異なる課題が2つある。

### 1.1. 第一の課題：露出（ngrokの罠）

* **ユーザーの背景**:
  データを外部クラウド（OpenAI等）に送信せず、機密情報を100%手元に閉じ込めるためにローカルLLMやDifyを導入している。
* **課題**:
  社外のテスターやスマホ実機から一時的に検証する際、公式に推奨されている「ngrok」等を利用せざるを得ない。しかし、これによって「全世界にパブリックURLが露出する」「中央集権の海外サーバーを経由する」というリスクが発生し、ローカルに閉じ込めていたはずの機密レベルが崩壊している。

### 1.2. 第二の課題：共有した先に制御が無い

* **Ollama・LM Studio 等のローカル推論エンドポイントには認証機構が無い。** ポートに到達できた者は誰でもそのGPUを叩ける。SentinelOne と Censys の調査（2026年1月）では、無認証・ファイアウォールなしの Ollama ホストが130カ国で **175,000台**公開されていた。
* **「経路」はすでに無料で埋まっている。** Tailscale・Cloudflare Tunnel が自宅/オフィスのGPUへ外から繋ぐ手段を無料で提供しており、Tailscale はローカルAI向けの導線を自ら訴求している。
* **埋まっていないのは「共有した先」。** Tailscale の推奨する *VPN as trusted perimeter*（ネットワークに居れば認証済みとみなす）は境界までしか担保せず、API レベルの認証・クォータ・記録は「nginx や API ゲートウェイを自分で立てて足せ」とされている。**誰に・何を・どれだけ貸したかを制御する層が空いている。**

## 2. ターゲットセグメント（フェーズ1のペルソナ）

* ローカル環境で Dify、Flowise、Open WebUI、自作のローカルLLMアプリを検証しているエンジニア。
* **開発中の MCP サーバーを、社内ゲートウェイに登録する前にチームメイトへ見せたい開発者。**
* **1台の高価なGPU箱を複数人で共有している小規模開発チーム。**
* クライアントのデータを扱うため、ngrok などのパブリックURL発行ツールを情シス（情報システム部門）から禁止されている開発チーム。
* ハッカソンやコワーキングスペースなどのパブリックWi-Fi（クライアント間通信禁止環境）で、隣のメンバーに安全かつ爆速でローカルサーバーを共有したい開発者。

## 3. InstantMeshが提供する圧倒的価値

InstantMesh は、上記2つの課題を**「アカウントレス」「使い捨て（エフェメラル）」「完全P2Pクローズド接続」「共有先の統制」**というアプローチで解決する。

* **全世界への隠蔽（URLレス）**:
  公開URLは一切発行されない。ホストの生成したQRコード/リンクから、ホストが承認した特定のゲストだけが同じ仮想LAN（ルームごとに 10.x 系プライベートレンジから /24 を払い出す）に入り、Dify等（ポート80/8080等）にアクセスできる。
* **データ主権の死守（完全P2P）**:
  シグナリング完了後は端末間で直接暗号化パケット（WireGuard）をやり取りするため、データが外部サーバーを通過せず、機密情報が100%担保される。
* **設定に書ける宛先（安定した名前）**:
  共有されたサービスに `http://ollama.tanaka.mesh:11434` のような**セッションをまたいで変わらない名前**で到達できる。メッシュIPはルームごとに払い出されるため毎回変わるが、名前は変わらないので `.env`・手順書・CI にそのまま書ける。OS の DNS を変更できない環境向けに、ゲストの `127.0.0.1` へ同一ポートで出す代替手段も用意する。
* **ホスト側を `0.0.0.0` に開かせない**:
  一般的なリモートアクセス手順が要求する `OLLAMA_HOST=0.0.0.0` 相当の設定を**不要**とする。当該設定こそが上記175,000台の露出を生んでおり、それを避けることを設計要件とする。
* **一時的な貸与と回収**:
  待合室承認で個別に貸し、キックで即座に取り上げ、時間経過で自動的に消滅する。常設 tailnet では「一時的」を、公開トンネルでは「隔離」を表現できない。
* **共有先の統制（有料）**:
  誰が・どのサービスを・どれだけ使ったかを記録し、ゲストごとにアクセスキーと上限を与える。認証機構を持たない推論エンドポイントに、外から統制を被せる。

> 旧版に記載していた「無料版のポート制限による安全担保」は**撤廃済み**である。E2E 暗号化された直通経路はサーバーからポート単位で選別できず、クライアント側フィルタは改変でバイパス可能で悪用抑止として実効性がないため（`docs/要件定義書.md` §4.5・付録B B-3）。

## 4. 戦わない領域（意図的な非スコープ）

差別化を維持するため、以下には正面から挑まない。

* **個人が自宅/オフィスのGPUに外から繋ぐ常設用途** … Tailscale の土地。無料枠（6ユーザー）で足り、彼ら自身がこの用途を訴求している。奪えない。
* **社内MCPサーバーの本番配信・中央ガバナンス** … MCPゲートウェイ各社（2026年時点で十数社）の土地。企業は中央で統制しやすい配置を選んでおり、検索上位の MCP サーバーの約8割はベンダーホストのリモート提供である。

狙うのは、この2つの隙間にある**「中央に載る前」と「中央に載せられないもの」**である。

* 社内ゲートウェイに登録される前の、作者のノートPCで動いている MCP サーバー
* ローカルにしか無いもの（手元のファイル、開発中のDB、外に出せないオンプレ機器）を触る MCP
* 集約が遅れる推論エンドポイント（GPUは高価で分散し、そもそもデータを外に出さないためにローカルに置かれている）
* 信用できない第三者製 MCP サーバー（調査された1,808サーバーの66%に何らかのセキュリティ上の発見）を、隔離された一時的な網の中でだけ動かす用途

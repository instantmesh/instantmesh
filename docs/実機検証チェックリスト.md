# 実機検証チェックリスト

CI（`.github/workflows/ci.yml`）が検証できない範囲——**特権を要する OS 設定・実 NIC・実 NAT・実サービスへの到達**——を手動で確認するための手順書。`TODO.md` に「残: 実機検証」と記された項目に 1 対 1 で対応する。

- **CI が見るもの**: `pkg/` の純粋ロジック（100% カバレッジ）・型崩れ（クロスビルド）・脆弱性。
- **CI が見られないもの**: 仮想NIC の生成とアドレス付与、`:53` の bind、split DNS の注入と回収、`127.0.0.1` バインドのサービスへの到達、共有外ポートの遮断、実 NAT 越しの UDP 穴あけ、実際のポート衝突とプロセス再起動をまたぐ決定性。**本チェックリストの対象はここだけ**。
- 合格した項目は `TODO.md` の該当行から「残: 実機検証」を外し、本書末尾の記録表に日付・OS・結果を残す。

各項目は **【手順】→【合格条件】→【外れたときの切り分け】** の形で書く。切り分け欄は「実装の不具合か、環境要因か」を分けるための指示であり、ここを飛ばすと 4 段重ねの層（転送・到達制御・名前解決・L7）のどこで失敗したのか判別できない。

## 0. 前提

### 0.1 機材構成

| 役割 | 要件 |
| :--- | :--- |
| **ホスト機**（貸す側） | Windows 11 / macOS / Linux のいずれか。**管理者/root 権限が必須**。共有するサービス（Ollama 等）が動いている |
| **ゲスト機**（借りる側） | ホスト機とは別のマシン。V-14 以外は同一 LAN でも可 |
| **サーバー** | シグナリング（`/ws`）＋リレー（`/relay`）。両機から到達できる場所に 1 台（LAN 内の PC で足りる） |

現状の実機検証実績は **ParrotOS×2（VMware NAT）でのメッシュ疎通まで**。Windows / macOS のホスト経路（NRPT・`netsh`・`/etc/resolver/`・`ifconfig`）は未検証のため、**まず Windows をホスト機とする構成を優先する**（未検証範囲が最も広い）。

### 0.2 なぜ管理者権限が要るか（権限不足時の症状を切り分けるため）

| 操作 | 権限 | 失敗時の挙動 |
| :--- | :--- | :--- |
| 仮想NIC の生成（`-tunnel`） | 管理者/root | 起動時に「仮想NIC起動」エラーで終了 |
| メッシュIP 付与・ルート設定 | 同上 | 警告のみでシグナリングは継続（`configureTunnel` が warn に留める） |
| メッシュIP の `:53` bind | 同上 | 警告のみ。名前解決だけ無効（メッシュIP 直接は使える） |
| split DNS 注入（`-dns`） | 同上 | 同上 |

**「権限が無い」と「実装が壊れている」は同じ見え方をしない**——上表のとおり前者は警告で続行するため、ログに `warn` が出ていたら必ず権限を先に疑う。

### 0.3 起動コマンド

```powershell
# サーバー（どちらの機材からでも到達できる 1 台で）
go run ./cmd/server -addr :8080

# ホスト機（Windows: 管理者 PowerShell から。GUI が既定モード）
go run ./cmd/client -server "ws://<サーバーIP>:8080/ws?tier=pro" -cognito-domain= -account dev-account

# ゲスト機（Linux: root。ヘッドレス CLI。招待リンクはホストの GUI からコピーする）
sudo go run ./cmd/client -mode guest -invite "instantmesh://join?..." -nick alice
```

**`?tier=pro` はアクセスキー・上限・利用記録（Pro 限定・§5）の検証に必須。** `DevAuthenticator` はクエリ `tier=pro` を Pro と見なす（`cmd/server/auth.go`）。付けなければ Free で動き、V-09〜V-12 は「402 この機能は有料プランでのみ利用できます」になる——**これは正しい挙動であり不具合ではない**。なお Cognito 認証を有効にした場合はトークンの `cognito:groups` が正で、クエリでは昇格しない（`cmd/server/cognito.go`）。

招待リンクにはこのクエリ付き URL がそのまま埋め込まれる（`pkg/invite` が `url.Values` で符号化するため往復する）。ゲストは `role=guest` で接続し `tier` は無視されるので、そのまま貼ってよい。

### 0.4 被験サービスの用意

**共有するサービスは `127.0.0.1` にバインドしていること**——ここが D-10（ホスト側転送）の検証の要。`0.0.0.0` バインドだと転送を経ずに直接到達してしまい、転送が壊れていても気付けない（実装は bind 失敗を検知して「既に全アドレスで待ち受けているため転送しません」とログを出す。この行が出たら D-10 の検証にはなっていない）。

本番相当は **Ollama**（既定 `127.0.0.1:11434`）。無い場合は下記スタブで代用する。V-11（ストリーミング）と V-04（遮断）の両方に使えるよう、**共有する `127.0.0.1:11434` と、共有しない `0.0.0.0:9000` の 2 つを立てる**。

```go
// scratch/verifystub.go — go run scratch/verifystub.go で起動（検証用。リポジトリには含めない）
package main

import (
	"fmt"
	"net/http"
	"time"
)

func main() {
	mux := http.NewServeMux()
	// 単発応答（到達確認用）
	mux.HandleFunc("/api/tags", func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprint(w, `{"models":[{"name":"stub"}]}`)
	})
	// 逐次応答（V-11: ストリーミングが途切れないことの確認用）
	mux.HandleFunc("/stream", func(w http.ResponseWriter, r *http.Request) {
		w.Header().Set("Content-Type", "application/x-ndjson")
		for i := 0; i < 10; i++ {
			fmt.Fprintf(w, "{\"chunk\":%d}\n", i)
			w.(http.Flusher).Flush()
			time.Sleep(500 * time.Millisecond)
		}
	})
	// 共有しないサービス（V-04: 到達制御で落ちることの確認用）。0.0.0.0 で待ち受ける点が重要。
	go func() { _ = http.ListenAndServe("0.0.0.0:9000", mux) }()
	// 共有するサービス（127.0.0.1 限定 = 転送が無いと届かない）
	_ = http.ListenAndServe("127.0.0.1:11434", mux)
}
```

### 0.5 既知ポート表（検出・名前の対象）

`pkg/localsvc`: 11434=Ollama / 1234=LM Studio / 8000=vLLM / 8080=Open WebUI / 3000=開発サーバー / 80=Dify。表に無いポートは `port-<番号>.<ラベル>.mesh` の名前になる。

## 1. 検証項目

### 土台（ここが崩れていると以降の切り分けが成立しない）

#### V-01 仮想NIC の生成・メッシュIP 付与・疎通

【手順】
1. ホスト機で GUI を起動し、ルームを作成する。
2. ゲスト機で招待リンクから参加し、ホストの GUI で承認する。
3. 双方でインターフェースとルートを確認する。

```powershell
# Windows（ホスト）
Get-NetIPAddress -InterfaceAlias wg-mesh
netsh interface ipv4 show route | Select-String "10.0.0"
```

```bash
# Linux（ゲスト）
ip addr show wg-mesh && ip route | grep 10.0.0
ping -c 3 <ホストのメッシュIP>
```

【合格条件】双方に `/32` のメッシュIP が付き、メッシュ `/24` が `wg-mesh` 経由になっている。ゲストからホストへ `ping` が通る。

【切り分け】
- ping が通らない: まず `wg-mesh` の存在とアドレスを確認。付いていなければ権限（0.2）。付いているのに通らなければ **ホスト側 OS のファイアウォール**を疑う——Windows Defender ファイアウォールは新規インターフェースを「パブリック」と判定して受信 ICMP を落とすことがある。`New-NetFirewallRule` で一時的に許可して切り分ける（恒久設定は行わない）。
- それでも通らなければ WireGuard ハンドシェイクが成立していない → V-14 / V-15 側の問題として扱う。
- 既存ネットワークとメッシュ `/24` が重複する環境では「既存ネットワークとの重複により仮想NICの設定を中止しました」が出る（`ErrSubnetConflict`）。環境要因であり実装の不具合ではない。

### 共有層（§4.6 / §4.7）

#### V-02 ローカルサービス検出（§4.6.1）

【手順】ホストのスタブ（または Ollama）を起動した状態で GUI の共有候補一覧を開く。`GET /api/services` の結果が画面に出る。

【合格条件】起動しているサービスが `Detected: true` で候補に出る。**プローブは TCP connect までで HTTP は送らない**ため、スタブ側のアクセスログにリクエストが記録されない。

【切り分け】検出されない場合、そのサービスが本当にループバックで待ち受けているか（`netstat -ano | Select-String 11434`）。走査先は `127.0.0.1` と `::1` のみで、LAN アドレスにしか bind していないサービスは検出対象外（仕様）。

#### V-03 ホスト側転送（D-10）— `127.0.0.1` バインドへ届くこと

【手順】
1. GUI で `11434` を共有する（`POST /api/share`）。
2. ホストのログに「共有サービスの転送を開始しました listen=<メッシュIP>:11434 target=localhost:11434」が出ることを確認。
3. ゲストから `curl http://<ホストのメッシュIP>:11434/api/tags`。

【合格条件】ゲストから応答が返る（`{"models":...}`）。**これは転送が無ければ絶対に成立しない**（サービスは `127.0.0.1` にしか bind していない）。

【切り分け】
- 「既に全アドレスで待ち受けているため転送しません」が出ている場合、被験サービスが `0.0.0.0` bind になっている → 0.4 をやり直す（この状態で到達できても D-10 の検証にはならない）。
- 「共有サービスの転送を開始できませんでした」なら bind 失敗。メッシュIP がインターフェースに付いているか（V-01）を先に確認する。
- 転送は **TCP のみ**。UDP サービスは対象外（仕様）。

#### V-04 到達制御（D-11）— 共有していないポートが遮断されること

**本項目が「共有の選択が広告ではなく強制である」ことの唯一の証明。** 共有していないポートは転送もされていないため、遮断が効いていなくても「繋がらない」ように見えてしまう。そこで **`0.0.0.0:9000`（メッシュIP でも待ち受けてしまうサービス）** を使い、`-share-guard` の有無で差が出ることを確認する。

【手順】
1. 共有は `11434` のみ（`9000` は選ばない）。
2. ゲストから `curl --max-time 5 http://<ホストのメッシュIP>:9000/api/tags` → **落ちること**を確認。
3. ホストを `-share-guard=false` で再起動し、同じ手順を実行 → **繋がること**を確認。
4. `-share-guard=true`（既定）へ戻す。

【合格条件】手順 2 が**タイムアウト**（`Connection refused` や `RST` ではなく無応答）で、手順 3 は成功する。この差分が出て初めてフィルタが効いていると言える。

**無応答であることが重要**——実装は落としたパケットを黙って捨て、RST も ICMP unreachable も返さない（共有していないポートの存在を相手に知らせないため）。`Connection refused` が返る場合はフィルタではなく OS が拒否している（＝フィルタを通過している疑い）。

【切り分け】手順 2 と 3 で差が出ない場合、`-tunnel` が有効か（フィルタは `tun.Device` を包むため仮想NIC 無しでは効かない）、共有選択が実際に反映されているか（ホスト GUI の共有中サービス表示）を確認する。

#### V-05 ICMP と名前解決が遮断されないこと（付録C.9.1 の必須要件）

【手順】V-04 の状態（`-share-guard` 既定・共有は `11434` のみ）で、ゲストから
1. `ping -c 3 <ホストのメッシュIP>`
2. `dig @<自分のメッシュIP> ollama.<ホストラベル>.mesh`（自機のレスポンダへ直接問う）

【合格条件】いずれも成功する。ICMP は共有の有無と独立に常に許可され、自メッシュIP の `:53` も同様（`controlPorts()`）。

【切り分け】ここが落ちるのは実装の不具合（フィルタの許可リスト漏れ）。`pkg/pktfilter` のユニットテストは通っているため、疑うのは `applyFilterPolicy` に渡す自アドレスの取り違え。**この項目の失敗は付録C.9.1 で明示された必須要件の違反であり、他の項目より優先して修正する。**

#### V-06 名前解決（§4.6.3）— 注入と解決

【手順】
1. ホスト・ゲスト双方で split DNS が注入されたことを確認する。

```powershell
# Windows: NRPT に自分の規則が入っているか
Get-DnsClientNrptRule | Where-Object { $_.Comment -eq 'InstantMesh' } | Format-List Namespace, NameServers, Comment
```

```bash
# Linux（systemd-resolved）
resolvectl status wg-mesh
# macOS
scutil --dns | grep -A 3 "domain.*mesh"
```

2. ゲストから名前で到達する: `curl http://ollama.<ホストラベル>.mesh:11434/api/tags`

【合格条件】NRPT の `Namespace` が `.mesh`、`NameServers` が自分のメッシュIP。名前での `curl` が成功する。ホスト自身の GUI に出ている URL も同じ名前で開ける（ホストは自分の名前を自分のゾーンにも入れる）。

【切り分け】
- **名前が配布されない最頻の原因は `-stun=` による STUN 無効化**——名前は `peer_info` に相乗りするため、WAN エンドポイントが確定しないと配布されない（既知の制約）。メッシュIP 直接（V-03）は動くのに名前だけ引けない場合、まずここを疑う。
- 注入は成功しているのに引けない場合、レスポンダ自体を直接叩いて層を分ける（V-05 の手順 2）。直接なら引けるのに OS 経由で引けないなら OS 設定側、直接も引けないならレスポンダ／ゾーン側。
- **DNS over TCP は未対応**（応答は 512 バイト未満に収まるため stub リゾルバは UDP で完結する）。`dig +tcp` で試すと失敗するが仕様。

#### V-07 split DNS の残骸回収（§4.6.3 の必須要件）

エフェメラル訴求（§4.3）に直結する。**異常終了しても OS に設定が残らないこと**を確認する。

【手順】
1. セッション稼働中（V-06 合格状態）で、クライアントプロセスを**強制終了**する（`Stop-Process -Force` / `kill -9`。正常終了ではないことが重要）。
2. NRPT に規則が残っていることを確認する（残るのが正しい——強制終了では解除処理が走らない）。
3. クライアントを**もう一度起動**する（ルーム作成前でよい）。
4. 再度 NRPT を確認する。

【合格条件】手順 4 で `Comment -eq 'InstantMesh'` の規則が消えている（`cleanupStaleSplitDNS` が `main` 冒頭で無条件に走る）。**他者の NRPT 規則（Comment が異なるもの）は消えていない。**

【切り分け】残骸が消えない場合は権限（非特権実行では回収もできない・0.2）。他者の規則まで消えていた場合は目印による絞り込みが壊れており、**影響が利用者の環境に及ぶ重大な不具合**として扱う。

#### V-08 スコープ厳守 — `.mesh` 以外の解決経路を変えないこと

【手順】セッション稼働中に、通常の名前解決が変化していないことを確認する。

```powershell
Resolve-DnsName www.google.com        # 通常どおり解決する
Resolve-DnsName ollama.<ラベル>.mesh  # 自分のメッシュIP へ解決する
```

【合格条件】前者が従来の DNS サーバー経由で解決し、応答元・所要時間が普段と変わらない。後者だけがメッシュIP を返す。

【切り分け】通常の解決が壊れる／遅くなる場合は注入範囲が広すぎる。設計上ここは譲れない一線（要件 §4.6.3・設計原則2 の精神）なので、**他の項目が全部通っていても本項目が落ちたらリリース不可**として扱う。

#### V-09 アクセスキー（D-16・Pro 限定）

【手順】
1. `?tier=pro` でホストを起動していることを確認（0.3）。
2. GUI でゲストにキーを発行する（`POST /api/control` の `issueKey`）。表示されたキーを帯域外でゲストへ渡す。
3. GUI でキー要求を ON にする（`{"requireKey": true}`）。
4. ゲストから **キー無し**でアクセス: `curl -i http://ollama.<ラベル>.mesh:11434/api/tags`
5. ゲストから **キー付き**でアクセス: `curl -i -H "Authorization: Bearer <キー>" http://ollama.<ラベル>.mesh:11434/api/tags`
6. GUI でキーを再発行し、**古いキー**で 4 と同じ要求を出す。

【合格条件】4 は `401` ＋ `WWW-Authenticate: Bearer` ＋ `{"error":"アクセスキーが必要です"}`。5 は成功。6 は `401`（再発行で旧キーは即時失効）。`X-InstantMesh-Key: <キー>` でも 5 と同じ結果になる。

【切り分け】
- 4 が `200` を返す場合、**L7 ゲートが立っていない**可能性が高い。ゲートはキー要求 ON か上限設定ありのいずれかで初めて立ち、それまでは生 TCP 転送のまま（`gateLocked`）。手順 3 を実際に反映できているか（GUI の状態表示・`GET /api/control` の `requireKey`）を確認する。
- `402` が返る場合は Free プラン（0.3）。
- キー要求の ON/OFF は**待受を張り替える**（生 TCP 転送 ⇄ HTTP プロキシ）ため、切替時に既存接続が切れる。これは仕様。

#### V-10 ゲスト単位の上限（§4.7）

【手順】
1. ゲスト A・B の 2 台を参加させる（B が用意できない場合は本項目は A のみで実施し、記録表に「B 未実施」と残す）。
2. A に `maxRequests: 3` を設定する（`{"limit":{"pubKey":"<Aの公開鍵>","maxRequests":3}}`）。
3. A から 4 回続けてリクエストする。
4. 直後に B からリクエストする。

【合格条件】A の 4 回目が `429` ＋ `{"error":"利用上限に達しました"}`。**B は影響を受けず成功する**（上限超過は当該ゲストのみを遮断し、ルーム全体には影響させない）。

【切り分け】B まで落ちる場合は上限の紐付けキー（接続元メッシュIP）の取り違え。上限判定は**キーではなく接続元アドレス**で行う設計（キーは「誰として使うか」の申告に過ぎない）。

#### V-11 ストリーミング応答が途切れないこと

L7 プロキシを挟むと推論のトークン逐次出力が壊れうる（バッファリング）ため独立項目とする。

【手順】キー要求 ON の状態で、ゲストから `curl -N -H "Authorization: Bearer <キー>" http://ollama.<ラベル>.mesh:11434/stream`（Ollama なら `POST /api/generate` の `stream: true`）。

【合格条件】チャンクが**到着ごとに逐次表示**される（10 行が 0.5 秒間隔で出る）。全部まとめて最後に出た場合は不合格（`FlushInterval: -1` が効いていない）。

#### V-12 利用記録（§4.7・Pro 限定）

【手順】V-09〜V-11 を実施した後、GUI の利用記録（`GET /api/usage`）を開く。

【合格条件】ゲスト別・ポート別に `bytesIn` / `bytesOut` が計上され、L7 を通した経路では `requests` も増えている。**プロンプトや応答本文は一切含まれない**（記録は接続メタデータと数量のみ・設計原則4）。Free プランでは `available: false`。

【切り分け】`bytesOut` が 0 のまま増えない場合、応答方向の計上（`Read` 側・送信元ポートが共有ポートであること）の判定漏れ。`requests` が 0 なのは L7 ゲートが立っていない場合の正常値（L4 のみの経路）。

#### V-13 即時解放（§4.6.4 の要件）

ホストが元ポートを占有し続けると、ゲストが自分の同種サービスを起動できなくなる。**解放が遅れないこと**を確認する。

【手順】共有中に以下をそれぞれ実施し、直後にホスト機で待受が消えていることを確認する（`netstat -ano | Select-String "<メッシュIP>:11434"`）。
1. GUI で共有を解除する（空配列を送る）。
2. ゲストを退出させる／ホストがルームを解散する。
3. ブラウザ（GUI）を閉じる（ハートビート途絶で切断される）。

【合格条件】いずれの場合も待受が直ちに消え、確立済み接続も切れる。共有解除後にゲストから `curl` すると到達できない。

### 土台（続き・NAT）

#### V-14 独立した実 NAT 間の UDP 穴あけ（要件 §7 の KPI 判定を兼ねる）

前回の検証は同一 NAT 配下だったため経路判定が未確認。**別の回線**（例: ホストは自宅回線、ゲストはモバイル回線テザリング）で実施する。

【手順】双方 `-tunnel` 有効・`-stun` 既定で接続し、ハンドシェイク成立後にホストのログで経路を確認する。GUI のピア表示が `Direct` になることを見る。

【合格条件】リレーへ転落せず直通で疎通する。要件 §7 は成功率 80% を求めるため、**回線・NAT の組み合わせを変えて複数回試行し、記録表に試行数と成功数を残す**（1 回の成功では KPI 判定にならない）。

【切り分け】対称NAT × 対称NAT は設計上リレー必須（対象外）。`-tunnel=false` では WireGuard と別ソケットで STUN するためマッピングがずれる（既知の限界）——検証は必ず `-tunnel` 有効で行う。

#### V-15 直通⇄リレーのフォールバック

【手順】V-14 の構成で、直通が成立しない状況を作る（一方の UDP を FW で塞ぐ等）。ログとピア表示の遷移を追う。

【合格条件】`Probing` から一定時間後に `Relay` へ遷移し、疎通が回復する（`ping` が通る）。サーバー側はリレー転送量を計上するが、**復号はしない**。

#### V-17 loopback プロキシ（副の経路・§4.6.4）

**ゲスト側の待受を扱う唯一の項目。** 主経路（名前解決）とは独立に、`-loopback` を付けたゲストで確認する。この経路の価値は「ポートが保存されること」と「衝突時も**毎回同じ**ポートへ退避すること」にあり、後者はプロセスを再起動して初めて確認できる。

【手順】
1. ゲスト機で `-loopback` を付けて参加する（要 `-tunnel`。ホスト側の設定は変わらない）。

```bash
sudo go run ./cmd/client -mode guest -loopback -invite "instantmesh://join?..." -nick alice
```

2. ホストが `11434` を共有した状態で、ゲストから `curl http://127.0.0.1:11434/api/tags`。
3. ゲスト機で**自分の** Ollama（または 0.4 のスタブ）を `127.0.0.1:11434` に立ててから、`-loopback` 付きで参加し直す。ログの「loopback プロキシを開始しました」の `local` と、GUI の共有中一覧に出る `http://127.0.0.1:<代替ポート>` を確認する。
4. ゲストのプロセスを終了し、**もう一度**同じホストへ参加し直す。代替ポートが手順 3 と同じ値であることを確認する。
5. ホストが共有を解除する（GUI で空にする）。直後にゲスト機で待受が消えていることを確認する（`ss -ltnp | grep 11434`）。
6. ゲストを退出させる／ホストがルームを解散する。同じく待受が消えることを確認する。

【合格条件】
- 手順 2 で応答が返る（元ポートが空いていればポート保存）。待受は `127.0.0.1` のみで、`0.0.0.0` や LAN アドレスでは待ち受けていない（`ss -ltnp` の Local Address が `127.0.0.1:...`）。
- 手順 3 で代替ポートは `20000` 以上 `30000` 未満。**ゲスト自身の Ollama は起動したまま動いている**（プロキシが元ポートを奪わない）。GUI に「元のポートが使用中のため別ポートで待受中」が出る。
- 手順 4 で手順 3 と**同じ**代替ポート（決定的な導出。ここが変わるなら本経路の目的を満たしていない）。
- 手順 5・6 で待受が直ちに消え、確立済み接続も切れる。

【切り分け】
- 待受が開かない: `-loopback` を付けたか（既定は無効）、`-tunnel` が有効か（転送先のメッシュIP へ到達できないと無意味なため起動しない）。ログに「loopback プロキシの待受ポートを確保できませんでした」が出ていれば全候補が埋まっている（異常に近い状態。名前解決またはメッシュIP 直接へ案内する）。
- 代替ポートが毎回変わる: `pkg/portmap` の導出はホスト公開鍵と元ポートのみに依存するため、**ホストが鍵を作り直している**（＝ホスト側プロセスの再起動）可能性が高い。招待リンクの SAS が前回と同じかを確認する。
- 応答が返らないのに待受はある: 転送先（ホストのメッシュIP:元ポート）へ到達できていない。V-03 / V-04 を先に通す。
- **TCP のみ**（UDP は対象外・仕様）。

### 設定の永続化（付録C.9 D-14）

#### V-16 メッシュ名と共有の選択がセッションをまたいで安定すること

§4.6.2 の「セッションをまたいで名前が安定する」は**実際に再起動して初めて確認できる**（ゲストは `http://ollama.<ラベル>.mesh:11434` を `.env` や手順書へ書く）。同時に、**保存内容に秘密が混ざっていないこと**（設計原則3）を目視で確かめる。

【手順】
1. GUI（idle 画面またはホスト画面）の「メッシュ名」を変更して「名前を保存」。続いて共有するサービスを選び「共有を更新」。
2. 設定ファイルの中身を目視する。

```powershell
# Windows
Get-Content "$env:AppData\InstantMesh\config.json"
```

```bash
# macOS
cat ~/Library/Application\ Support/InstantMesh/config.json
# Linux（$XDG_CONFIG_HOME 未設定時）
cat ~/.config/InstantMesh/config.json && ls -l ~/.config/InstantMesh/
```

3. クライアントを終了し、`-mesh-name` を**付けずに**もう一度起動する。
4. GUI の「メッシュ名」表示と、ルーム作成後の共有中サービス一覧を確認する。
5. `-config=`（空文字）で起動し直し、名前を変更してから再起動する。

【合格条件】
- 中身は `version` / `meshLabel` / `sharedPorts` の 3 項目のみ。**WireGuard 秘密鍵・招待トークン・アクセストークン・アクセスキーが含まれない。**Unix 系ではファイル `600`・ディレクトリ `700`。
- 手順 4 で名前と共有の選択が復元され、前回ゲストへ渡した名前付き URL がそのまま使える。
- 手順 5 では保存されず（次回起動で既定の名前へ戻る）、GUI に「設定の保存は無効です（-config）」と出る。`-mesh-name` を付けた起動ではフラグが保存値より優先される。

【切り分け】
- 保存されない: ログの「クライアント設定を保存できませんでした」（書き込み権限・パス）を見る。`-config=` で無効化していないか。
- 復元されない: 設定の版が自身より新しい場合は読み込みを拒否し既定値で続行する（ログに警告。この場合は**上書き保存も止まる**）。
- 共有の選択が一部だけ復元される: プランの同時共有サービス数（Free=3・§5）で切り詰められている。仕様であり不具合ではない。

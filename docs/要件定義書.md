# 要件定義書：InstantMesh（フェーズ1）

> **2026-07-27 方向転換**: 前面に出す姿を「汎用のアカウントレス一時メッシュVPN」から「**ローカルAI／MCP を、公開せずに一時的に人へ貸すためのアクセス層**」へ寄せた。汎用メッシュ機能（任意ポート・汎用ルーム）は削らず土台として残す。判断の根拠・経緯・却下した代替案は**付録C**に記録する。付録A（レビュー結果）・付録B（レビュー対応方針）は当時の記録であり、遡及改変しない。

## 1. プロダクト概要
ユーザーが事前設定や面倒な登録なしに、**手元で動いているローカルAI（ローカルLLM／MCP サーバー／開発サーバー）を、公開URLを発行することなく、特定の相手へ一時的に貸し出せる**ソフトウェア。基盤は安全な仮想ローカルネットワーク（Mesh VPN）であり、その上に「共有するサービスを選んで貸す」導線と「誰にどれだけ貸したかを制御する」層を持つ。

* **最大の特徴**: ネットワークを開く人（ホスト）だけがサービスのアカウント（ホストアカウント）を持ち、参加する人（ゲスト）はアカウント登録不要（アカウントレス）で利用できる点。
* **第二の特徴**: 共有されたサービスはゲストの `127.0.0.1` に**同じポート番号のまま**出るため、ゲストは既存ツールの接続先設定を書き換えずに利用できる（§4.6）。

### 1.1. 解決する課題とターゲット（プライマリ・ペルソナ）
* **プライマリ・ペルソナ**: **ローカルAI／リモート開発者および小規模開発チーム**。ローカルLLM（Dify＋ローカルLLM等）・MCP サーバー・開発サーバーを、チームメンバーやリモート環境と一時的かつ安全に共有したいが、既存VPNの常設セットアップやポート開放・固定的なアカウント管理を避けたい層。
* **コアな課題（2層）**:
    1. **露出**: ローカルに閉じ込めた機密を、共有のために ngrok 等でパブリックURL化してしまい前提が崩壊する。
    2. **共有先の無統制**: Ollama・LM Studio 等のローカル推論エンドポイントには**認証機構が無い**ため、ポートに到達できた者は誰でもGPUを叩ける。経路（どう繋ぐか）は Tailscale・Cloudflare Tunnel が無料で埋めた一方、「誰が・何を・どれだけ使えるか」を制御する層が空いている。
* **注記**: 本ペルソナを唯一の基準とし、プラン・成功指標・訴求はすべてこれに従属させる（ゲーマー／イベント等のカジュアル層は主対象外）。
* **意図的な非スコープ（戦わない領域）**: ①個人が自宅/オフィスのGPUへ外から繋ぐ**常設**用途（Tailscale が無料枠で提供し自ら訴求している領域）、②**社内MCPサーバーの本番配信・中央ガバナンス**（MCPゲートウェイ各社の領域）。狙うのは「中央ゲートウェイに載る**前**」と「中央に**載せられない**もの」（`docs/vision.md` §4）。

## 2. スコープと成功指標

### 2.1. やること（フェーズ1の対象）
* デスクトップ3種（Windows / macOS / Linux）向けのアカウントレス即席Mesh VPN。
* ホストのアカウント認証、ルーム作成・待合室承認・キック、エフェメラルなライフサイクル管理。
* **ローカルサービス共有（§4.6）**: 起動中のローカルサービスの検出、ポート番号を保存したままの共有、ゲスト側 loopback への露出。
* **共有先の統制（§4.7）**: 共有単位の利用記録と、ゲストごとのアクセス制御（有料プラン機能。仕様確定＋実装まで。決済は除く）。
* 無料／有料のプラン差の**仕様定義**（機能制限の実装を含む。決済は除く）。

### 2.2. やらないこと（フェーズ1のスコープ外）
* **決済・課金の実装**（有料プランの提供機能は仕様として確定するが、課金処理は後続フェーズ）。
* **モバイル（iOS / Android）対応**（VPN審査・OS制約が重いため後続フェーズ）。
* GPUマーケットプレイス等の派生プロダクト（§8 将来展望を参照）。
* マルチAZ／完全冗長化構成（スケール時に移行。§6・§7参照）。

### 2.3. フェーズ1の成功指標
フルファネルKPIは時期尚早とし、**検証仮説1本＋合否基準**に絞る。

* **検証仮説**: 「ローカルAI／リモート開発者は、**手元のローカルAIを公開せずに一時的に人へ貸す**ことに継続的な利用価値を見出す」。
* **合否基準（仮）**:
    * ターゲット開発者による**ルーム再作成（リピート）率 ≥ 40%**（初回利用者のうち2回目以降を作成した割合）。
    * **P2P（直接）接続成功率 ≥ 80%**（§7 非機能要件）。
    * **共有導線の到達率 ≥ 70%**: ホストが「共有するローカルAIを選ぶ」を開始してから、ゲストが実際にそのサービスへ到達するまでを完了した割合（§4.6 の導線が機能しているかの判定）。
    * クリティカルなUXブロッカー（接続失敗・切断の未回復）が主要フローで発生しないこと。

## 3. ユーザー体験（UX）フロー

### 3.1. ホスト（共有する人）
1. アプリを起動し、GitHubまたはGoogleアカウントで1クリックログイン（MFAは任意・推奨）。
2. **「共有するローカルAIを選ぶ」**（主導線）。起動中のローカルサービスが検出されて一覧表示されるので、共有対象を選ぶ（§4.6）。検出されない場合や任意のポートを共有したい場合は、ポート番号を直接指定する。
    * **副導線**として、サービスを選ばずに「汎用ルームを作成」することもできる（従来どおりメッシュ全体への到達性のみを提供する）。
3. 画面に接続用の **QRコード** および **インバイトリンク** が表示される（いずれもホストの公開鍵フィンガープリントを含み、帯域外検証に用いる）。
4. 制限時間（無料版：最大1時間 / 有料版：最大24時間）を設定する。
5. 待合室に届いた参加リクエストを、ゲストの**公開鍵フィンガープリント（SAS）とニックネーム**を確認して個別に承認／拒否する。
6. 運用中に招待URL/QRコードが意図せず漏洩した場合、「招待リンク再発行」ボタンで、既存の接続メンバーを維持したまま新しい招待URLへ即座にローテーションできる（旧URLは即時無効）。不審な既接続ゲストは「キック」で遮断する。

### 3.2. ゲスト（参加者）
1. アプリを起動し、ログインせず「ルームに参加」を選択。
2. ホストから受け取った招待リンク（`instantmesh://join?...`）を入力・貼り付けする（現状ゲスト側のQRスキャン/読み取りは未実装。QRはホスト側の表示のみ）。
3. 一時的なニックネーム（表示名）を入力し、参加リクエストを送信して待合室で待機する。
4. ホストが接続を承認すると、アカウント登録なしで、即座に仮想ネットワークに参加。
5. **共有されたサービスに、セッションをまたいで安定した名前で到達できる**（例: `http://ollama.tanaka.mesh:11434`）。名前は接続先設定・手順書・CI に書ける（§4.6.2 経路(1)）。UI は `http://` を含む完全なURLをコピー可能な形で提示する。
6. 割り当てられた専用のプライベートIP（例: `10.0.0.x`）を使った直接通信（Ping、割当IP経由のローカル共有、任意ポートへのアクセス）も従来どおり可能（経路(2)）。
7. OS の DNS 設定を変更できない環境では、ゲストの `127.0.0.1` に同一ポートで出す loopback プロキシを代替手段として使える（経路(3)・TCP のみ）。ポートが埋まっている場合は決定的に導出した代替ポートへ退避し、実際の待受を画面に明示する（§4.6.4）。

> 注: 「ファイル共有」は割当IP経由でSMB等のローカル共有に到達できるという接続性の説明であり、専用のファイル共有機能を提供するものではない。

## 4. 機能要件

### 4.1. アカウント・権限管理
* **ホスト**: システムが提供する認証基盤（Amazon Cognitoによるユーザー登録/サインイン）を必須とする。MFA（TOTP）は任意で提供（推奨）。ルームの作成、強制解散、接続承認（待合室フロー）、および不審なゲストのキック（遮断）権限を持つ。
* **ゲスト**: アカウント登録不要。認証・識別はホストが発行した「使い捨てのルームトークン」および一時的な「デバイス識別子（WireGuard公開鍵）」で行う。接続時に一時的なニックネームを入力し、ホストの承認（待合室フロー）を経て接続される。
* **招待トークン強度**: ルームトークンは推測不能とするため **128bit 以上を CSPRNG で生成**する。

### 4.2. ネットワーク（データプレーン）
* **P2P メッシュ通信**: プロトコルは **WireGuard** をベースとし、端末間はエンドツーエンド（E2E）で暗号化する。
* **NATトラバーサル**: カフェのWi-Fiなどの環境でも繋がるよう、STUN技術を用いた「穴あけ（Hole Punching）」を実装する。
* **リレー（フォールバック）**: P2P接続がどうしても失敗した場合のみ、暗号化パケットをそのまま中継するリレーサーバー（DERP 相当の自前リレー。宛先公開鍵ベースの転送で TURN は未使用）を経由させる。
* **鍵交換の完全性（MITM対策）**: QRコード／招待リンクに**ホストの公開鍵（またはそのフィンガープリント）を埋め込み**、シグナリングサーバーを経由しない帯域外（out-of-band）で検証する。これによりシグナリングサーバーが侵害されても中間者攻撃（MITM）を成立させない。ゲストの参加承認時には、ホスト画面に**ゲスト公開鍵の短縮フィンガープリント（SAS）** を表示する。

### 4.3. コントロールプレーン（管理機能）
* **シグナリング**: 接続開始時、端末同士が互いの暗号化公開鍵と一時IPを交換するためのWebSocket等の仲介システム。
* **IPアドレス割当**: ルームごとに `10.0.0.0/24` 等のレンジを確保し、ホストに `.1`、ゲストは参加順に順次割り当てる。キック・退出後のIPは一定時間の猶予後に再利用する。
* **エフェメラル（自動消滅）ライフサイクル**:
    * ホストが「解散」を押す、または設定された制限時間が経過した場合、シグナリングサーバー上のルーム情報を完全に削除する。
    * ルーム消滅時、全クライアントの仮想NIC（ネットワークカード）およびWireGuardの接続設定を自動的に破棄・クリーンアップする。
    * **無通信タイムアウト（Idle Timeout）**: 有料版・無料版問わず、ルーム内で**純アイドル（まったく通信が発生しない状態）が30分継続した場合のみ**、ゾンビセッション排除のため自動的にルームを解散する。通信が継続している限り（長時間の開発共有を含む）解散しない。

### 4.4. 状態遷移・エラー要件
* **待合室フロー（状態遷移）**:
    * 状態は「申請中（待合室）→ 承認 / 拒否 / 無応答タイムアウト失効 / キック済み」。
    * **承認前ネットワーク隔離**: 待合室段階ではWireGuardのピアを追加せず、仮想IPも割り当てない（シグナリング接続のみ）。承認されて初めてネットワークへ参加する。
    * **無応答タイムアウト（仮 120秒）**: ホストが一定時間承認・拒否しない場合、申請を自動失効させ、ゲストに再申請を促す。
    * **同時申請**: 複数ゲストの申請はキューで表示し、ホストが個別に承認／拒否する。
    * **踏み台DoS対策**: 1トークンあたり・1IPあたりの参加申請にレート制限をかける。
* **キック（遮断／再参加ブロック）**:
    * キック時、対象ゲストの**公開鍵とルームトークンをブラックリストに登録**し、WireGuardピアを削除してIPを回収する。
    * トークン失効のみでは新トークンで復帰可能なため、**公開鍵ベースのブロックを主**とし、ルーム存続中は同一鍵の再参加を拒否する。
* **招待URLの即時再発行**:
    * ホストの操作でルーム識別用セッショントークンを即座に再生成し、旧URL/QRコードからのアクセスをすべて無効（404）にする。**承認済みの既接続ピアは維持**される。
    * 注意事項として、**すでに漏洩した「承認済みの相手」の排除には再発行では不十分であり、キックの併用が必要**であることをUI上で明示する。
* **エラー系・例外系**（主要フローで必ずハンドリング・UI提示する）:
    * トークン失効・ルーム消滅時の通知と再取得導線／認証（Cognito）失敗／承認拒否・タイムアウトの通知／P2P確立失敗時のリレーフォールバック／リレー累計上限到達（速度制限）の通知／対称NAT等でP2Pもリレーも不能な場合の明示的な接続不可通知／切断からの再接続。

### 4.5. クラウドコスト・悪用対策
* **ポート制限は設けない（撤廃）**:
  かつて無料版にクライアント側デフォルトフィルタによるポート制限（Web・開発用ポートのみ許可）を設ける方針だったが、これを撤廃する。理由は次のとおり:
  * E2E 暗号化された P2P 直通経路はサーバーからポート単位で選別できず（選別できること自体が E2E 主張と矛盾する）、制御はクライアント自己申告に依存し**改変によりバイパス可能**。悪用抑止として実効性がない。
  * プライマリ・ペルソナ（開発者）の主要用途である SSH や UDP（DNS・QUIC 等）を無料枠で塞ぐことは UX を大きく毀損し、プロダクトの価値と衝突する。
  * 悪用抑止・コスト防御は**サーバー側で強制可能なレイヤ**（下記リレー通信量制限・レート制限・監査ログ）に一本化する。
* **リレー通信量制限**:
  AWSのデータ転送量課金（Data Transfer Out）のスパイクを防ぐため、**リレーサーバー経由の通信はプラン別の累計上限（無料プラン：1接続あたり100MB）に到達した時点で64kbpsへ速度制限**する（切断はしない。Ping/軽量API確認・LLM のテキスト推論ストリームなど軽通信は継続可能）。※P2P直接通信の場合は無制限。確定値は §5 を参照。
* **レート制限（リソース枯渇対策）**:
  1アカウントあたりの同時ルーム数・ルーム作成頻度に上限を設け、リレー悪用・ルーム量産によるリソース枯渇を防ぐ。

### 4.6. ローカルサービス共有

本プロダクトの主導線。メッシュ到達性の上に「特定のローカルサービスを、相手の手元から扱える形で出す」層を載せる。

#### 4.6.1. サービス検出（ホスト側）

* ホスト起動時に既知ポートを走査し、起動中のローカルサービスを一覧提示する。
* 既知ポート表（初期値）: `11434` Ollama / `1234` LM Studio / `8000` vLLM / `8080` Open WebUI / `3000` 開発サーバー / `80` Dify。
* **プローブは TCP connect までに留める**（HTTP リクエストを送ると誤検出・意図しない副作用を招くため）。検出結果はあくまで候補提示であり、共有可否はホストの明示選択による。
* 検出に失敗しても、ホストはポート番号を直接指定して共有できる。
* **ホスト側のサービスは `127.0.0.1` にバインドしたままでよい。** 一般的なリモートアクセス手順が要求する `OLLAMA_HOST=0.0.0.0` 相当の設定は**不要**とする。当該設定こそが無認証エンドポイント大量露出（§1.1）の原因であり、本プロダクトはそれを避けることを設計上の要件とする。

#### 4.6.2. ゲストからの到達方法

ゲストは以下の3経路で共有サービスへ到達する。**(1) を主とする。**

**(1) 名前解決（主）** — `http://ollama.tanaka.mesh:11434`

* ホストが定義した名前で到達する。**セッションをまたいで名前が安定する**ため、ゲストの `.env`・手順書・CI 設定に書ける。
* ポート衝突が起きず、TCP/UDP・任意プロトコルに等しく適用でき、ゲストのポートを占有しない。
* ルームごとの `/24` は `pkg/manager` が動的に払い出すためメッシュIPはセッションごとに変わるが、**名前は変わらない**。これにより固定IP予約（付録C.4 で却下）を不要にする。
* 構成は §4.6.3。

**(2) メッシュIP直接（従来・常に利用可）** — `http://10.0.0.1:11434`

* 既存の到達性。名前解決を導入しても削らない。UDP・ping・SMB・任意ポートを含む。
* セッションごとにアドレスが変わるため、設定ファイルに書く用途には向かない。

**(3) loopback プロキシ（副・DNS を触れない環境向け）** — `http://127.0.0.1:11434`

* OS の DNS 設定が MDM 等でロックされ (1) を適用できない環境のための代替手段。仕様は §4.6.4。
* **TCP のみ**を対象とする。UDP を使うサービスはこの経路に載らないため (1) または (2) を使う。

**前提: ホスト側の転送（`0.0.0.0` バインドを不要にするための必須部品）**

上記 3 経路はいずれも、ホスト側に転送が無ければ成立しない。**ホストのサービスが `127.0.0.1` にのみバインドしている場合、メッシュIP 宛のパケットは当該ソケットに受け付けられない**ためである。したがって §4.6.1 の「`0.0.0.0` バインドを要求しない」（D-9）を守るには、ホスト側でメッシュIP:ポート → `127.0.0.1`:ポート の転送を行う部品が要る（決定は付録C.9 D-10）。

* 転送は**ユーザ空間で行う**。OS の DNAT 設定（iptables / pf / netsh portproxy）は使わない——OS ごとに実装が割れ、異常終了時に残骸回収の責任が増えるため（`hosts` 書き換えと split DNS の選択と同じ理由・付録C.4）。
* **ポート番号は保存される。** `10.0.0.1:11434` と `127.0.0.1:11434` はアドレスが異なるため、ホスト側では衝突しない（ポート衝突が通常系になるのはゲスト側だけ・§4.6.4）。
* サービスが既に `0.0.0.0` にバインドしていてメッシュIP:ポートを bind できない場合は、**転送せずそのまま直接到達させる**（bind の可否がそのまま両者の判別になる）。
* ゲスト側 loopback プロキシ（経路(3)）と**転送コアは同一**とし、向きと待受アドレスだけを変えて使う。

#### 4.6.3. 名前解決の構成（権威はホスト、解決はローカル）

* **権威はホストにある。** ルームを所有し、IPを払い出し、共有するサービスを決めるのはホストであるため、名前空間を定義する主体もホストとする。
* **解決は各クライアントのローカルで行う。** ホストが定義した名前⇄メッシュIPの写像を**既存のシグナリング経路で配布**し、各クライアントが自プロセス内に持つレスポンダが即答する。**ホストにDNSサーバーを立ててゲストが参照する構成は採らない**（理由は付録C.4）。
* **OS への注入は split DNS で行う。** 当該サフィックスのみをローカルレスポンダへ向ける（Windows=NRPT / macOS=`/etc/resolver/<ドメイン>` / Linux=systemd-resolved 等の DNS マネージャ）。**`hosts` ファイルの書き換えは採用しない**（付録C.4）。
    * **スコープを厳守する。** 当該サフィックス以外のクエリの経路を変更してはならない。ゲストの通常のDNSトラフィックが本プロダクトの影響下に入ることは、設計原則2の精神に反する。
    * **異常終了時の残骸を起動時に無条件回収する。** エフェメラル訴求（§4.3）に直結するため、クリーンアップは必須要件とする。
    * サフィックスは `.local`（mDNS 予約）を使用しない。未知TLDをブラウザが検索語として扱う問題があるため、UI は `http://` を含む完全なURLをコピーさせる。
* **名前は信頼の根拠ではない。** 名前はホスト側の自己申告に由来し、別人が同じ名前を名乗りうる。ニックネームと同じく「自己申告・未検証」として扱い、**信頼の根拠はあくまで公開鍵の帯域外照合（SAS・§4.2）** であることを UI 上でも明示する。
* 権限: 管理者/root 権限は仮想NIC（`-tunnel`）で既に取得しているため、DNS 設定注入に伴う追加の権限要求は発生しない。

#### 4.6.4. loopback プロキシの仕様（代替手段）

* **ポート保存**: ゲスト側の `127.0.0.1` に**原則として同一のポート番号**で待ち受ける。`Host:` ヘッダを一致させることで、絶対URLを生成するアプリやオリジン検査の挙動をローカル実行時と揃える。
* **バインド範囲**: ゲスト側の待受は `127.0.0.1` のみに限定する（`0.0.0.0` にはバインドしない）。ゲストのLANへ再露出させないため。
* **ポート衝突は通常系として扱う。** ゲスト自身も同種のソフトを動かしている可能性が高く、複数ホストから同じポートのサービスを借りる場合は必ず衝突する。
    * 元ポートが空いていればそれを使う。
    * 衝突時の代替ポートは**決定的に導出する**。同じホスト・同じサービスなら毎回同じ値になること（例: `20000 + SHA256(ホスト公開鍵 ‖ 元ポート) mod 10000`、埋まっていた場合のみ線形探索）。**ランダムな空きポート割当は採用しない** — セッションごとにゲストが設定を書き換えることになり、本手段の目的を失うため。
    * 実際の待受ポートを UI に明示し、接続先文字列を**コピー可能な形**で提示する。
* **即時解放**: 共有停止・キック・ルーム解散・時間切れのいずれでも、ゲスト側の待受を直ちに閉じる。ホストが元ポートを占有し続けると**ゲストが自分の同種サービスを起動できなくなる**ため、UI から共有を個別に停止できることを要件とする。

#### 4.6.5. 層の位置づけ

* **純粋ロジック（`pkg/`）**: 既知ポート表の判定、ポート写像の定義と衝突解決、名前⇄メッシュIPの写像、DNSクエリの解析と応答の組み立て。
    * DNS メッセージの扱いは `pkg/stun`（メッセージ生成/解析は純粋、ソケットは `cmd`）と同じ分割に倣う。
* **I/O アダプタ（`cmd/client`）**: TCP リスナーと転送ループ（ホスト側の転送とゲスト側 loopback プロキシで共有する）、実際のプローブ、UDP ソケットとレスポンダの駆動、OS への split-DNS 注入（`dnsconfig_<os>.go`）と起動時の残骸回収。
* **製品固有の知識（Ollama や MCP のプロトコル解釈）を `pkg/` の汎用コアへ持ち込まない**（`CLAUDE.md` 設計原則8）。

### 4.7. 共有先の統制（有料プラン機能）

認証機構を持たないローカル推論エンドポイントに対し、外側から制御を被せる層。**無料プランは「貸せる」まで、有料プランは「誰にどれだけ貸したかを制御・記録できる」**という差にする（§5）。

* **利用記録**: 共有単位・ゲスト単位で、接続時刻・接続回数・転送バイト数を記録し、ホストの画面に提示する。
    * **記録はホスト側クライアントで行う**。サーバーは E2E 暗号化された通信の中身を復号できず、また復号してはならないため（設計原則2）、サーバー側での計上は行わない。
    * 記録するのは接続メタデータと数量のみ。**プロンプト・応答本文などの通信内容は記録しない**（設計原則4と同一の方針）。
* **ゲストごとのアクセスキー**: 共有サービスへのアクセスに、ゲストごとに異なるキーを要求できる。キーの失効はキックと独立に行える。
* **ゲストごとの上限**: ゲスト単位のリクエスト数・転送量に上限を設定し、超過時は当該ゲストのみを遮断する（ルーム全体には影響させない）。
* **将来拡張（フェーズ1スコープ外）**: MCP のツール呼び出し単位での承認・記録。既存の待合室承認は「ピアの参加」単位であり、ツール呼び出し単位への拡張はプロトコル解釈層を要するため後続とする（付録C.4）。

## 7. 非機能要件

* **開発言語**: サーバー、クライアントともに **Go言語** をベースに構築する。
* **セキュリティ（E2E暗号化）**: サーバー（AWS）側はシグナリングの仲介と暗号化パケットのリレーを行うのみであり、ユーザー間の通信内容（データ）を**復号・閲覧できない**構造にすること。鍵交換の完全性は §4.2 のホスト鍵ピン留め／SAS照合で担保し、シグナリングサーバー侵害時のMITMを防止する。
* **鍵・秘密情報の管理**: クライアントのWireGuard秘密鍵は、メモリロック（mlock）・使用後のゼロ化・スワップ抑止を行い、ディスク／スワップへの露出を防ぐ。
* **監査ログ（法的防衛線）**: 「どのホストアカウントが、いつルームを作成し、どのIPアドレスのゲストが参加したか」という**接続メタデータのみ**を保持する（**通信内容は保持しない**）。
    * 保持期間: **3ヶ月（仮）**。電気通信事業法の該当性判定（後述の並行タスク）を踏まえて確定する。
    * 保護: S3 Object Lockによる改ざん防止、KMSによる暗号化、アクセスは最小権限に限定。
    * **利用規約との整合**: 「記録は技術的に不可能／痕跡ゼロ」といった表現は用いず、「通信内容は復号・閲覧しないが、接続メタデータは保持する」旨をToSに明記する。
* **データ保護・プライバシー**: ゲストのIPアドレス等は個人データとして扱う。ゲストの参加時に**プライバシー通知＋同意**を取得し、保持期間・削除方針を提示する。リージョンは東京固定で越境移転は行わない。
* **可用性・性能（定量目標）**:
    * ネットワーク接続性: 一般的なパブリックWi-Fiにおいて **P2P（直接）接続成功率 80%以上**（必達目標）。
    * P2P接続確立時間: 目標 **10秒以内**（仮）。
    * 想定同時ルーム数・同時接続数の上限を定義し、超過時の挙動（新規作成の制限等）を明示する。
    * 監視・アラート、基本的なDDoS対策（レート制限・接続数制限）を備える。
* **対応プラットフォーム**: フェーズ1は **Windows / macOS / Linux のデスクトップ**を対象とする（モバイルは後続）。

> **並行タスク（法務）**: 他者通信をリレー媒介することによる**電気通信事業法の該当性**（届出要否・通信の秘密・開示対応）は弁護士判定を並行で進め、結果を監査ログ保持期間・開示対応フローに反映する。

## 8. 将来的な展望（C2C GPUプラットフォームへの拡張ビジョン）

本プロジェクト（InstantMesh）は、「アカウントレスかつ手軽に構築できる一時的な仮想プライベートネットワーク（VPN）」として独立したサービスであり続けます。

将来的には、InstantMeshの接続技術（P2P通信、NATトラバーサル、リレー）をSDK / ライブラリとして切り出し、別プロダクトであるC2C GPUシェアリング・マーケットプレイスの通信基盤として内部利用する構想です。

### 8.1. プロダクト構成（2サービス体制）
* **InstantMesh（本プロダクト）**: 即席VPNサービスとして独立して開発・運用・マネタイズする。
* **GPUマーケットプレイス（別プロダクト・別ブランド）**: C2C GPUシェアリングの独立したサービスとして開発する。内部の通信レイヤーにInstantMeshのSDKを利用する。

### 8.2. GPUマーケットプレイスの概要
* **概要**: 余剰GPUを「貸したい人（ホスト）」と「借りたい人（ゲスト）」を直接マッチングするC2Cプラットフォーム。
* **アカウント要件**: InstantMeshとは異なり、GPUマーケットプレイスでは貸し手・借り手の双方にユーザー登録を必須とする。決済（売上の受け取り・利用料の支払い）および不正利用時の本人特定が必要なため。
* **VPN技術の応用**: 借り手が貸し手のGPUマシン（または隔離されたコンテナ）に対して、ポート開放不要でセキュアにアクセスするためのネットワークトンネルとしてInstantMeshのSDKを利用する。
* **追加予定の要素**:
    * **セキュリティ隔離（サンドボックス）**: 貸し手のPC本体や家庭内LANを保護するため、GPUリソースのみをパススルーしたDockerコンテナ等へのアクセス制限。
    * **マッチング＆決済**: GPUスペック、価格、貸出時間に応じたマッチングシステムおよび時間単位の自動決済機能。
    * **検証メカニズム**: 提供されるGPUのスペックや稼働状況（Uptime）を自動検証・評価する機能。

### 8.3. SDK化に向けた設計指針
InstantMeshの開発時から、将来的にコア通信機能をSDKとして切り出せるよう、以下の点を意識して設計する。
* **UIとコアロジックの分離**: VPN接続処理（WireGuard制御、シグナリング、NATトラバーサル）をUIに依存しない独立パッケージ（`pkg/`配下）として実装する。
* **APIの汎用性**: シグナリングやリレーの接続インターフェースを、InstantMeshのUI専用ではなく、外部プロダクトからも呼び出せる汎用的なAPI設計とする。

| C6 | PIN 4桁ブルートフォース対策なし | 機能・非機能(R-2)・ビジネス | 1万通り総当たり可能、レート制限・ロックアウト・トークン強度が未定義。シーケンス図にPIN照合ステップすら無い |
| C7 | 待合室フローの分岐欠落（拒否／無応答タイムアウト／同時申請／踏み台DoS） | 機能・ビジネス・非機能(M-3) | 承認=許可経路のみ定義。日常的に起きる主系フローが未定義 |
| C8 | キック（遮断）機能がほぼ未定義 | 機能 | 権限宣言のみ（3.1）。再参加ブロック（トークン/公開鍵ブラックリスト）なしではキックが無意味化 |
| C9 | 単一障害点＋非機能の定量目標欠如 | 非機能(R-3,M-7)・ビジネス | シグナリング兼リレーが単一t4g。冗長化・スケール・DDoS・SLO・監視が無く、定量値はP2P成功率80%のみ。ホストも単一障害点 |
| C10 | ゲスト個人情報(IP)の同意・保持・越境 | 非機能(R-6) | ゲストは無登録参加で同意フロー無し。IPは個人データ（GDPR）、リージョン・越境移転根拠が未定義 |

#### 🟡 中（推奨）

- **なりすまし／ニックネーム非検証**（機能11・ビジネス6・非機能M-2）— 承認判断が表示名のみ。3名重複
- **エラー系・エッジケースがほぼ皆無**（機能6・ビジネス1）— トークン失効UI／認証失敗／再接続／ポート弾き通知など
- **ポート制限の実効性**（ビジネス2・非機能M-1）— クライアント自己申告依存でバイパス可能、「物理的防止」は不成立
- **100MB到達時／対称NAT最悪ケースの挙動未確定**（機能7,8・非機能D-3）
- **KPI／成功指標の欠如**（ビジネス4）
- **リレー悪用・ルーム量産のレート制限なし**（非機能M-5）、**ホストMFA未定義**（M-6）、**秘密鍵のGC/スワップの穴**（M-4）
- **対応プラットフォーム未定義＋モバイルVPN/管理者権限の整合**（ビジネス3）
- 招待URL再発行の状態遷移（機能9・非機能D-4）、IP割当ロジック（機能10）、Idle 30分と長時間開発共有の衝突（ビジネス7）

#### 🟢 軽微

「やること／やらないこと」節が無い（ビジネス）、「例：」表記の確定値化（機能13）、ワンタイムパス未反映、「ファイル共有」の位置づけ、パスコード「オプション/標準」の差不明 ほか

### A.3. デビルズアドボケイトの反論のうち、検討に値するもの

批判役は「どう直すか」ではなく「そもそも作る/直す価値があるか」を突いた。リーダー評価として是々非々で採否を付す。

#### 採用すべき（鋭く、意思決定に効く）

1. **価値仮説の構造的自壊（異議1・2・4）— 最重要**
   「WTPがある層（開発チーム）は既にアカウントを持ちTailscale等で足りる／刺さるカジュアル層は¥500を払わない」「手軽さはアプリ導入＋管理者権限で相殺されURLを踏むだけのngrok/Cloudflareに劣る」「E2Eの信頼保証とアカウントレスは両立しない」。→ **ペルソナを1つに決めても解けない**という指摘は正当。要件を精緻化する前に価値仮説の検証が要る。

2. **ポート制限は「調整」でなく「削除」を検討（対ビジネス2への反論）**
   E2E暗号化トンネル内をサーバーがポート単位で選別できるなら、それ自体がE2E主張と矛盾。制御はクライアント自己申告依存でバイパス可能。→ 悪用防止としてほぼ無意味かつUX毀損。削除も選択肢。

3. **監査ログとToSは文言修正で直らない二律背反（C4の格上げ）**
   ログを持てば「記録不可能・痕跡ゼロ」訴求が虚偽になり、持たなければ法的防衛線が消える。→ マーケ・法務・技術の三者択一であり経営判断事項。

4. **電気通信事業法を「後で評価」でなく事業成立性の前提リスクへ格上げ（C5）**
   単価¥500のB2Cに届出・通信の秘密・開示対応の負荷は重い。→ 着手前の意思決定材料。

5. **PIN機能自体の要否を問う（対機能5への反論）**
   人間が待合室で承認する設計なら、PINは冗長な第二の壁の可能性。→ 「対策を足す」前に「機能を削る」を先に検討。

6. **見落とされた実現可能性リスク（追加）**
   ①クロスプラットフォーム配布・署名工数（Wintun/EV署名、macOS公証+Network Extension、iOS VPN審査、Android VpnService）、②**決済・課金がスコープに存在しない**のに有料版を謳う、③スケジュール・体制・コストの前提が皆無。

#### 割り引いて扱うべき（一理あるが行き過ぎ）

- **「KPI完備要求は過剰」（対ビジネス4）**: フルファネルKPIは時期尚早に同意。ただし「フェーズ1の成功をどう判定するか」の定義は不可欠。→ フルKPIではなく“検証仮説1本＋合否基準”に絞る折衷。
- **「IP割当は軽微」（対機能10）**: 実装詳細として軽微化は妥当。ただしゲスト数上限・キック後IP再利用と絡むため、データ設計の一項目としては残す。
- **「GPUビジョンは踏み台になっていない（異議5）」**: 技術的連続性の弱さは正当な警告。フェーズ1の投資判断を「独立事業の採算」で行うべきという主張として扱えば十分。

#### リーダー留保

批判役の全体トーンは「作るな」寄りだが、最終判断はユーザーのもの。批判役の価値は「作らない理由」ではなく「作るなら何を先に確かめるべきか」を明確にした点にある。

### A.5. 各担当レビュー詳細

#### A.5.1 ビジネス・ユーザー視点

**重大**
- ターゲット／ペルソナがドキュメント間で矛盾（要件§1／vision§2／競合分析§1.1,1.2,3.2）。要件定義書自体に課題・ターゲット記述なし。
- 無料プランのポート制限（80/443/3000/5000/8080+ICMP=Web開発者向け）が、競合分析の主要ターゲット（ゲーマー・ファイル共有）と矛盾。PLGの入口が市場と噛み合わない。
- プラン数値がドキュメント間不整合＋ゲスト数上限（最重要転換レバー）が要件から欠落、Teamプランは競合分析のみ。
- ビジネスKPI/成功指標がほぼ未定義（測定可能なのはP2P80%とログ数ヶ月のみ）。

**中**: ①ユースケースがハッピーパスのみ（ホスト切断=単一障害点、複数ゲストのメッシュ、再接続）。②PIN総当たり/参加リクエストスパム。③対応プラットフォーム未定義、管理者権限とモバイル(iOS VPN制約)の整合。④監査ログが必須NFRかTeam有料機能か矛盾＋保持期間曖昧。⑤ToSの制限時間記述が実仕様と不整合。⑥ニックネーム重複・なりすまし。⑦Idle30分が長時間ローカル開発共有と衝突。

**軽微**: ①「やらないこと」明示セクションなし。②ワンタイムパスが要件プラン表に未反映。

#### A.5.2 機能要件

**重大**: ①最大ゲスト数の要件が全面的に欠落（3章/4章表 L60-73）。②プラン構成・制限値がドキュメント間で不整合。③キック機能の仕様がほぼ未定義（L33のみ、再参加ブロック不明）。④待合室フローに拒否/タイムアウト/同時申請が欠落。⑤PINにブルートフォース対策と検証タイミング定義なし（シーケンス図にPIN照合なし）。

**中**: ⑥エラー系・例外系の要件がほぼ存在しない。⑦100MB到達時の挙動が「切断または速度制限」で未確定。⑧対称NATで両端末接続不可+リレー上限超過の最悪ケース未定義。⑨招待URL再発行の状態遷移・制限未定義。⑩IPアドレス割当ロジック未定義。⑪ニックネームのバリデーション・重複時挙動未定義。

**軽微**: ⑫「オプション利用可/標準利用可」の差不明。⑬確定値が「例：」表記（Idle例30分、監査ログ数ヶ月）。⑭「ファイル共有」の位置づけが誤解を招く。

**曖昧・主観的な記述の一覧**: 3.3(L46)無通信タイムアウト「例:30分」／3.4(L56)リレー速度制限「例:64kbps」／4章(L70)Proリレー「制限緩和（または従量課金）」／4章(L72)パスコード「オプション/標準」／6章(L92)監査ログ「最低数ヶ月間」／6章(L93)「80%以上を目指し」（努力目標か必達か不明）。

#### A.5.3 非機能要件・セキュリティ

**重大**
- **R-1** シグナリングサーバー侵害時の鍵交換MITM（鍵配布経路がシグナリング自身、フィンガープリント検証なし、「侵害されても盗聴不可能」の主張が崩れる／アーキ4.1 L157-159）。
- **R-2** PIN 4桁ブルートフォース＋招待トークン強度・レート制限未定義。
- **R-3** シグナリング兼リレーが単一t4g＝単一障害点・スケールアウト/冗長化/DDoS対策/SLO/監視の欠如。
- **R-4** 監査ログの改ざん防止・保持期間・アクセス制御未定義＋ToS「記録は技術的に不可能」と矛盾。
- **R-5** 電気通信事業法の該当性・通信の秘密の取り扱い未評価。
- **R-6** ゲストのIP等個人情報の同意・通知・保持・越境（個情法/GDPR）欠落。

**中**: M-1 ポート制限バイパス（「物理的防止」不成立）。M-2 なりすまし（ニックネーム非検証）。M-3 待合室の踏み台/DoS・承認前のネットワーク隔離未明記。M-4 秘密鍵メモリ管理のGC/スワップの穴。M-5 リレー悪用・ルーム作成のリソース枯渇（レート制限なし）。M-6 ホストMFA未定義。M-7 非機能の定量目標の全般的欠如。

**軽微**: D-1 数値不整合。D-2 ゲストToS非同意。D-3 100MB到達後の挙動。D-4 再発行しても承認済み漏洩相手は排除不可。

#### A.5.4 デビルズアドボケイト（批判役）

**前提への異議**: ①アカウントレスは金を払う層に無価値、刺さる層は金を払わない（WTPと差別化の分離）。②「QRを読むだけ」は虚偽（アプリ導入＋管理者権限が必須、ngrok/Cloudflareに手軽さで劣る）。③コア用途とインフラ制約が衝突（大容量共有が100MBで即死、コアターゲットほど対称NATでP2P失敗）。④セキュリティを厳密化するほどアカウントレスが死ぬジレンマ（R-1は修正不能）。⑤GPUビジョンは技術的に繋がっていない（GPU用途は両者アカウント必須でフェーズ1固有機能を使わない）。

**代替案（D案）**: コア技術とクロスプラットフォームアプリの自作前に、既製品（Tailscale tsnet / NetBird / Cloudflare Tunnel）の薄いラッパーで価値仮説（WTP）を10〜20人に検証。最初の投下先は「技術が動くか」でなく「誰が金を払うか」。

### A.6. 総括

技術・アーキテクチャの筋は通っているが、視点を変えるたびに同じ穴が浮かんだ。特に「プラン不整合＋ゲスト数欠落」「待合室/キック等の状態遷移欠落」「PIN耐性」「監査ログ⇔ToS矛盾」「ターゲット矛盾」は複数レビュアーが独立検出した構造的欠陥。

また、要件の穴の多く（PIN・ポート制限・待合室・ログ矛盾）は「その機能を作らなければ発生しない」もので、精緻化するほど自己矛盾が深まりかねない。

**推奨する順序**: ゲート0（特に G0-1 ペルソナ確定・G0-2 WTP検証・G0-3 法務判定）を先に通し、その結果を踏まえてフェーズ1a/1bの要件修正に入る。

### B.4. ドラフト確定（既定値・要件へ反映）

技術的最適解が定まっているため、以下の内容で要件へ反映した。

#### B.4.1 待合室フローの状態遷移（C7 / A-3）
- 状態: 申請中（待合室）→ 承認 / 拒否 / 無応答タイムアウト失効 / キック済み
- **無応答タイムアウト = 仮120秒** で申請を自動失効。ゲストに再申請を促す
- **同時申請**: 複数ゲストの申請をキューで表示し、ホストが個別に承認/拒否
- **レート制限**: 1トークンあたり・1IPあたりの参加申請にレート制限（踏み台DoS対策）
- **承認前ネットワーク隔離**: 待合室段階ではWireGuardピア未追加・仮想IP未割当（シグナリング接続のみ）

#### B.4.2 キック（再参加ブロック）（C8）
- キック時に**ゲストの公開鍵＋ルームトークンをブラックリスト登録** → ピア削除・IP回収
- トークン失効のみでは新トークンで復帰可能なため、**公開鍵ベースのブロックを主**とする（ルーム存続中は同一鍵の再参加を拒否）

#### B.4.3 なりすまし補強（🟡 ★★★）
- 承認画面にゲスト公開鍵の**短縮フィンガープリント(SAS)** を表示。ニックネームは自己申告のため「未検証」ラベルを付す
- ニックネームは長さ・使用文字をバリデーションし、ルーム内重複時は自動サフィックス（例 `#2`）を付与

#### B.4.4 その他（🟡/🟢 まとめ処理）
- **エラー系要件節を新設**: トークン失効UI／認証失敗／再接続／ポート弾き通知／100MB到達通知
- **招待URL再発行の状態遷移**: 旧トークンを即時失効(404)し承認済みピアは維持。ただし**既に漏洩した承認済み相手の排除はキック併用が必要**と明記（D-4）
- **IP割当ロジック**: `10.0.0.0/24` 等からホストに `.1`、ゲストは順次割当。キック後のIPは一定時間後に再利用
- **Idleタイムアウト**: 「純アイドル（無通信）30分」のみを対象とし、通信中（長時間の開発共有含む）は解散しないことを明記
- **レート制限（ルーム量産）**: 1アカウントあたりの同時ルーム数・作成頻度に制限（リレー悪用・リソース枯渇対策）
- **秘密鍵管理**: メモリロック(mlock)／使用後ゼロ化／スワップ抑止をNFRに明記
- **「やること/やらないこと」節を新設**
- **「例:」表記の確定値化**: Idle=30分（確定）、リレー速度制限=64kbps（確定）、監査ログ保持=3ヶ月（仮確定）、P2P成功率80%=必達目標として記述
- **ファイル共有の位置づけ**: 「割当IP経由でローカル共有(SMB等)が可能」という接続性の説明にとどめ、機能保証ではないことを明確化
- PIN削除に伴い「パスコード（オプション/標準）」関連記述を削除

### C.2. 課金軸を変更する根拠（競合の実態調査）

改訂前の Free/Pro 差は「ゲスト数 5→20 / 制限時間 1h→24h / リレー 100MB→無制限」で、**すべて量の増量**だった。これが継続課金（サブスクリプション）の動機として成立しないと判断した根拠は以下である。

* **判定基準**: 有料機能は「**解約した瞬間に、すでにある手順やファイルが壊れる**」ものでなければ継続しない。量の制限は解約しても困らない（次回また無料枠でやればよい）ため、量課金が自然に売るのは**サブスクではなく都度課金（ワンタイムパス）**である。
* **Tailscale は個人向け有料プラン「Personal Plus」を廃止した。** 公式の料金改定告知によれば、相当数の利用者が「必要だからではなく、Tailscale を応援したいから」契約していたことを理由に挙げている。同社は無料 Personal を6ユーザーまで開放し、「料金の境界が明確さより躊躇を生むなら、消すべきなのはその境界だ」と述べている。**個人向けに量を増やしただけの有料プランは、実例として失敗している。**
* **Tailscale の収益は組織向けの統制と証跡**（SSO/SCIM・設定変更の監査ログ・ネットワークフローログ・SIEM 連携・デバイスポスチャ・ACLグループ数 3/10/300）に集中している。
* **ngrok の最大の課金ドライバは「自分の不便」ではなく「相手に出せない」こと。** 無料枠にはブラウザ訪問者向けの警告ページ（interstitial）が挿入され、有料化で消える。さらに独自ドメイン持ち込みは、Stripe の webhook 設定や OAuth の redirect URI といった**他人の設定に刻まれる**ため解約できなくなる。なお ngrok は無料枠の**セッション時間制限を撤廃済み**であり、時間による区切りを課金軸から外している。
* **導出される法則**: ①課金するのは「他人が絡む地点」、②他人の設定に刻まれるものを売る、③個人向けの量的増量は成立しない。§5 の「統制と記録」への移行はこの3点に沿う。

### C.3. 無料プランに残すもの（有料化してはならないもの）

* **セキュリティ機能全般**（待合室承認・キック・SAS照合・招待URL再発行・E2E暗号化）。これらを有料化すると「安全に共有できる」という訴求そのものが崩壊する。
* **ローカルサービス共有そのもの**（§4.6）。共有できること自体は無料に置き、**共有先の統制**（§4.7）で課金する。
* なお ngrok の interstitial に相当する「無料版では相手に出せない」型の施策は、同社の場合フィッシング対策という正当性の上に成立している。本プロダクトで**セキュリティ機能を人質に取る形で同じ手法を採ることはしない**。

### C.4. 却下・保留した案

| 案 | 判断 | 理由 |
|----|:---:|------|
| B を別サービス・別バイナリとして開発 | ✗ 却下 | D-3 のとおり。仮想NIC/ルートの競合と、獲得ユーザーの分断 |
| ゲストのメッシュIPを固定して設定ファイルに書かせる | ✗ 却下 | ①ルームごとの `/24` は `pkg/manager` が動的に払い出すため、最終オクテットを固定しても安定しない。②固定化すると利用者の実LAN（`10.0.0.0/8` は家庭・社内で多用）との衝突から復帰できず、`pkg/netcfg` が入れるルートによって当該サブネット宛通信を壊す |
| 固定名前解決（MagicDNS 相当）を `hosts` 書き換えで実装 | ✗ 却下 | `hosts` の改ざんは EDR/アンチウイルスの監視対象であり、**情シスに ngrok を禁止された開発チーム**というペルソナに対して致命的。加えて異常終了時にシステムファイルへ行が残り、エフェメラル訴求と矛盾する。採用するのは split DNS（Windows=NRPT / macOS=`/etc/resolver/` / Linux=systemd-resolved 等）＋起動時の残骸回収（§4.6.3） |
| **ホストに DNS サーバーを立て、ゲストがメッシュ越しに参照する** | ✗ 却下 | ①**最大のコストを回避できない** — ゲスト端末の OS split-DNS 設定とクリーンアップは同じだけ必要で、変わるのは向き先アドレスだけ。節約できるのは各クライアントの小さなレスポンダのみで、コストの比率が逆。②解決がネットワーク往復になり、DNS 失敗特有の長いタイムアウト・ネガティブキャッシュを招く。③ブートストラップの鶏卵 — メッシュ断時にクエリがハングする（ローカルなら即 SERVFAIL を返せる）。④ホストが名前解決の単一障害点になる（付録A C9 の SPOF を悪化させる）。⑤**ホストがゲストの DNS クエリを見られる** — スコープ設定を誤ると全クエリが流れ、設計原則2の精神に反する。⑥ホスト機の `:53` は Docker DNS・systemd-resolved・dnsmasq 等と競合しうる。**ただし「名前空間の権威はホスト」という発想自体は正しく、D-8 として採用した**（権威と解決を分離する） |
| loopback プロキシで `127.0.0.2` 等の別ループバックアドレスを使いポート番号を保存する | ✗ 却下 | Linux/Windows は `127.0.0.0/8` 全体がループバックだが、**macOS は既定で `127.0.0.1` のみ**構成され `ifconfig lo0 alias` が必要になり、OS に残る状態とクリーンアップ責任が増える。しかもゲストは `127.0.0.1`→`127.0.0.2` と書き換えるため、**ポートを書き換えるのと手間が同じ**で利点が薄い |
| 衝突時の代替ポートをランダムな空きポートから割り当てる | ✗ 却下 | セッションごとに待受ポートが変わり、ゲストが毎回設定を書き換えることになる。ポート保存の目的（設定変更ゼロ）を自ら失う。**決定的な導出**とする（§4.6.4） |
| MCP のツール呼び出し単位での承認・記録 | ⏳ 保留 | 既存の承認は「ピアの参加」単位であり、呼び出し単位への拡張はプロトコル解釈層を要する。フェーズ1スコープ外（§4.7） |
| ワンタイムパス（都度課金） | ⏳ 保留 | 量的需要（一時的な大人数・長時間）の受け皿としては引き続き有効。ただしティア判定を**ルーム作成時に確定してルームへ焼き付ける**設計変更が前提（現行 `pkg/plan.TierForGroups` は Cognito グループの在／不在で期限の概念を持たないため） |

### C.5. 前提として残るリスク・未検証事項

* **付録A.5.4 の批判役 異議①③に対する回答という位置づけ**: 「WTPがある層は既に Tailscale 等で足りる」「大容量共有が100MBで即死する」という指摘に対し、付録B の G0-2 では「事前検証せず開発に進む・市場リスクは受容」と決定していた。本方向転換は、その受容していた市場リスクへの回答である。ただし**WTP そのものは依然として未検証**であり、リスクが解消したわけではない。
* **競合の位置は不利である**: 経路の提供では Tailscale・Cloudflare Tunnel が無料で先行し、社内MCPの中央ガバナンスでは MCPゲートウェイ各社が先行している。本プロダクトが取れるのは両者の隙間（§1.1 の意図的な非スコープ）に限られ、市場規模は小さい。
* **Ollama 等が自前で共有・認証機能を実装する可能性**。ただし2026年時点で Ollama には認証機構が無く、それが無認証ホスト175,000台の露出（SentinelOne / Censys 2026年1月）を生んでいるため、統制レイヤは当面空いていると見込む。

### C.7. ゲスト到達手段の主従を入れ替えた根拠（D-7）

当初は loopback プロキシ（ポート保存）を主導線としたが、以下により**名前解決を主・プロキシを副**へ改めた。

* **「設定変更ゼロ」が成立するのはポートが空いているときだけ。** プライマリ・ペルソナのゲストは**自分でもローカルLLMを動かしている**確率が高く、`11434` 等は埋まっている。**最も熱心なユーザーほど約束が破れる**構造だった。
* **占有の副作用**: プロキシが元ポートを取ると、ゲストは後から自分の同種サービスを起動できない（`address already in use`）。共有が相手の環境を壊す。
* **TCP のみ**: UDP・ping・SMB を救えない。
* **複雑さがサービス数に比例する**: Pro は同時10サービス（§5）。リスナー・衝突解決・ライフサイクル・UI 表示がサービスごとに必要になる。対して名前解決は**ピア単位の仕組み**で、一度通せばそのピアの全ポート・全プロトコルに等しく効き、複雑さが増えない。
* **`/24` 不安定問題を同時に解く**: メッシュIPはセッションごとに変わるが名前は変わらないため、固定IP予約（C.4 で却下）が不要になる。ロックイン効果（他人の設定に刻まれる・C.2）も `http://ollama.tanaka.mesh:11434` の方が `http://localhost:21434` より強い。
* **プロキシを完全には捨てない理由**: OS の DNS 設定が MDM 等でロックされた企業端末が実在し、そこでは唯一の手段になるため（§4.6.2 の経路(3)）。

### C.8. 保留：無料枠の数値緩和案（D-5）

検討したが**採用を保留**した案。§5 の数値は `pkg/plan` の現行値（Free: 1時間 / 100MB）のままとし、ドキュメントを実装に一致させる方針を優先した。将来この判断を見直す際の材料として分析を残す。

| 項目 | 現行（実装済み） | 緩和案（保留） |
| :--- | :--- | :--- |
| 最大制限時間（Free） | **1時間** | 8時間 |
| リレー累計上限（Free） | **100MB** | 500MB（絞り速度 64kbps は据え置き） |

**緩和を検討した理由**:

* **制限時間**: 1時間ではローカルAIを共有した実作業（半日〜1日）の途中で切れ、§2.3 のリピート率 KPI と衝突しうる。ゾンビセッション排除は**純アイドル30分の自動解散**が主装置であり、通信が続く限り解散しない設計（§4.3）のため、上限時間を緩めてもコスト防御は保たれる。なお ngrok は無料枠のセッション時間制限を撤廃済みで、現行の1時間は同社の無料枠より厳しい。
* **リレー累計上限**: LLM の**テキスト**推論ストリームは 30 tok/s でも数百 B/s 程度であり、64kbps でも継続可能。したがって**絞り速度そのものは主用途を殺さない**。実際に効くのは累計上限へ到達する速さで、画像入力・音声・RAG 文書の投入・Web UI のアセット配信が 100MB を早期に消費する。

**保留した理由**:

* 数値変更は AWS のデータ転送コストに直結し、**実測なしに決めるべきではない**（緩和は上振れ方向にのみ効く）。
* 上記の課題が実際にどれだけ効くかは、共有層（§4.6）が動いてからでないと測れない。**先に実装、次に実測、最後に数値**の順が妥当。
* ドキュメントと `pkg/plan` の乖離を作らないことを優先した。**変更するときは §5 の表と `pkg/plan` を同時に更新する。**
